**Run:** from `services/`,
`docker build -f apps/api-stub/Dockerfile -t chain/api-stub . && docker run --rm -p 8080:8080 chain/api-stub`
**Base URL:** `http://localhost:8080/v1`. OpenAPI: `http://localhost:8080/v1/openapi.json`.
Details, fixtures and scenarios: `services/apps/api-stub/README.md`.

## Done

- `services/packages/shared/src/api/v1.ts`: zod schemas and inferred types for every request and
  response of all six spec 5.3 endpoints, plus the two 409 bodies and a common error body. Response
  objects are strict. `services/packages/shared/src/money.ts`: bigint helpers (`ceilDiv`,
  `refundAtomic`, string parse and format).
- `services/apps/api-stub/` (Hono on Node 22):
  - all six endpoints with deterministic fixtures: one `resourceId`, 800 USDC per night, and a
    three-cutoff curve materialised in `Europe/Athens` with Luxon (DST-correct)
  - every response is parsed through its schema before it is sent, so fixture drift is a 500, never
    bad data
  - all seven `x-stub-scenario` switches, comma-combinable; unknown or contradictory switches give 400
  - fake guest auth `stub-guest:<bookingId>` (401 when missing, 403 when for another booking)
  - prepare returns a spec 4.1 `quote` bound to `guestAddress`, a `bookingId` that is the real EIP-712
    `hashStruct(quote)`, and `calls` = `approve` and `deposit`, ABI-encoded against the spec
    signatures, with fake addresses and signature and `"stub": true`
  - OpenAPI 3.1 generated from the zod schemas, at `/v1/openapi.json`
  - multi-stage Dockerfile (non-root, healthcheck), with an optional build secret for proxy CAs
- ADRs `docs/adr/0001` to `0004` for everything that goes beyond spec 5.3 (see "Interfaces changed").

## Deviations from spec

None to spec text. Additions beyond spec 5.3 are ADR'd below. Choices where the spec is silent:

- **Prepared quote TTL is 15 minutes.** Spec 5.2 fixes only the 25-minute offer lock.
- **Offer ids are stateless.** They are base64url of `[checkIn, checkOut, guests]`, deterministic
  and restart-safe. Clients must treat them as opaque. C5 will use stored ids.
- **The stub does not enforce offer expiry at prepare.** Enforcing it would be business logic,
  which the brief puts out of scope.
- **`accruedYieldAtomic` means the guest's share of yield accrued so far, not vested.** Spec 5.3 does
  not say whether it is the booking's total `y` or the guest share. The agent-facing name and the
  allowlist (agent spec 7) point to the guest share. C5 and C6 must match this.
- **`availability` returns `[]` when guests exceed capacity**, and 400 `invalid_stay` for impossible
  dates (check-in not in the future, check-out not after check-in, more than 60 nights).

## Spec concerns

- The `cancelled` and `settled` scenarios are not contract states (review 0001 finding 7); resolved
  by ADR 0002.
- The Service API has no claim path, so guests never receive refunds or yield (finding 6);
  resolved by ADR 0003. ADR 0003 also records that a `[cancelByGuest, claim]` batch can revert as a
  whole for a blacklisted guest, so the checkout needs a fallback.
- `/v1/bookings/{bookingId}` has no escrow address in the path, and `bookingId` is not
  domain-separated (finding 16). This is fine for one escrow, but must be revisited before a second
  owner.
- Spec 5.3 marks `/v1/yield/terms?bookingId` as unauthenticated. It exposes only terms and an
  estimate, not booking details, but C5 should confirm that is intended.
